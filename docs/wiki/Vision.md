# Vision

Мы создаём Duro как распределённую платформу для объектов с состоянием, поведением и доступной историей. Разработчик загружает пакет кода, создаёт объект и вызывает его методы по постоянному ID. Метод получает аргументы, явно сохраняет нужные данные через хранилище и при необходимости возвращает значение. Платформа организует маршрутизацию, исполнение, долговечную фиксацию и восстановление после отказа исполнителя.

Мы хотим сделать чтение прошлых версий, создание независимых веток и откат данных частью работы с объектом. Разработчик сможет использовать эти возможности при отладке и включать их в функции своего приложения, например просмотр истории решений и сравнение вариантов плана.

Объём первой версии определён в [требованиях к MVP](Requirements.md). Откат является дополнительной возможностью; обновление кода с миграциями, CRDT, локальные реплики и офлайн-редактирование не входят в MVP.

MVP состоит из трёх модулей: маршрутизация и управление объектами, исполнение кода, хранение состояния и истории. Их взаимодействие скрыто за API Duro; разработчику приложения не требуется самостоятельно связывать исполнители с БД и управлять владением.

## Мотивация

При распределённом запуске приложения разработчику приходится связывать бизнес-логику с управлением состоянием. Нужно направлять запросы к исполнителю объекта, определять порядок изменений и сохранять подтверждённые результаты. После сбоя необходимо восстановить объект и обработать запросы, для которых клиент не получил ответ. Ошибки на этих границах могут привести к потере изменений или повторному применению одной операции.

Для разбора поведения приложения одного текущего состояния бывает недостаточно. Разработчику нужно увидеть, какие изменения привели к результату и с какими данными работало приложение. Чтобы проверить другой ход событий, ему потребуется восстановить прошлое состояние и продолжить работу с его копией.

## Целевая аудитория

Мы ориентируемся на разработчиков серверных и совместных приложений, в которых отдельные сущности меняются по заданным правилам, а история изменений нужна пользователю или разработчику. Это могут быть инструменты планирования или процессы согласования.

Duro проектируется для задач, где разработчику нужно обращаться к одной сущности из разных экземпляров приложения, сохранять её состояние при смене исполнителя и иметь доступ к прошлым версиям. Для совместных документов и рабочих пространств мы также хотим поддержать редактирование данных с нескольких устройств, в том числе при потере связи.

## Предлагаемые возможности Duro

Мы видим Duro как самостоятельный инфраструктурный продукт, который разработчик подключает к приложению через API. Он задаёт методы объекта и структуру сохраняемых данных, затем обращается к нему по постоянному идентификатору. Через объектный интерфейс разработчик сможет работать с текущими данными и историей, сохраняя контроль над правилами своего приложения.

Обновление кода существующего объекта рассматривается за пределами MVP. При обновлении новая версия сохраняется вместе с результатом преобразования данных.

В основу истории мы предлагаем положить журнал принятых изменений хранилища. По нему приложение сможет получить выбранную версию данных и создать из неё ветку с собственной дальнейшей историей. Для объяснения предметных решений разработчик сможет сохранять сведения об авторе и причине изменения вместе с данными приложения.

Например, в плане поездки можно будет открыть прежний список расходов и создать вариант с другим жильём. Ветка получит собственный идентификатор и будет меняться независимо от основного плана. Пользователь сможет сравнить варианты или вернуть основной план к прежним данным, сохранив историю правок.

Для совместной работы мы рассматриваем локальные реплики объекта на основе CRDT. Пользователь сможет изменять поддерживаемые данные без связи, а после подключения синхронизировать правки. Разработчик сможет сочетать такое редактирование с операциями, которые требуют серверной проверки. Например, участники будут редактировать общий черновик заявки, а на согласование отправлять конкретную версию. Последующие правки черновика не изменят отправленную версию.
