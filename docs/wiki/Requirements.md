# Требования к Duro

Duro предоставляет долговечные объекты с JavaScript-кодом и собственным KV-состоянием. Основная цель MVP — проверить распределённое исполнение под высокой и неравномерной нагрузкой, включая перенос объектов и восстановление после отказов.

Команда — три человека, срок первого MVP — восемь недель. Это проектные требования; достигнутые показатели фиксируются в отчёте по реализации.

## Основной сценарий

1. Разработчик загружает JavaScript bundle и манифест через `registerType`.
2. Создаёт объект через `create(object_id, type, version, input, request_id)`.
3. Вызывает `invoke(object_id, method, argument, request_id)`.
4. Получает `{ result, revision }` после долговечной фиксации. Отсутствие результата метода нормализуется в `null`.

Клиенту не нужны адрес исполнителя, поколение владельца и доступ к БД. Код явно сохраняет данные через `ctx.storage.get/put/delete`. Язык рабочих нод — Rust, среда обработчиков — V8 через `deno_core`. [Технические решения](Technical-Decisions.md) отвечают на вопросы о пакетах, runtime и БД.

## Три модуля

| Модуль | Ответственность |
| --- | --- |
| Маршрутизация и размещение, Go | Публичный API, приём пакетов, выбор владельца, маршруты, перенос и восстановление |
| Исполнение, Rust | V8, загрузка кода и состояния, очереди, планирование, буфер записей |
| Состояние и восстановление, язык открыт | Код, текущее состояние, владение, атомарная фиксация и результаты запросов |

Модули имеют отдельные сборки и тестируются через заглушки соседних API. Между ними — gRPC/Protobuf. Готовые БД и координатор не считаются дополнительными разрабатываемыми модулями.

## Что обязательно в MVP

- Регистрация типа и версии кода без пересборки рабочих нод.
- Создание, описание, вызов метода и чтение текущего состояния объекта.
- Последовательная обработка одного объекта и параллельная работа разных объектов.
- Атомарная фиксация, распознавание повторов и запрет записи старому владельцу.
- Автоматическое восстановление после падения исполнителя.
- Размещение по хешу и с учётом нагрузки; выбор политики конфигурацией.
- Добавление исполнителя и управляемый перенос между вызовами методов.
- Ограниченные очереди и явный отказ при перегрузке.
- Отказоустойчивое хранение с испытанием переключения PostgreSQL.
- Метрики, воспроизводимые нагрузочные прогоны и проверка корректности под нагрузкой.

Обязательны [FR-01–10](Functional-Requirements.md) и [NFR-01–10](Nonfunctional-Requirements.md).

## Гарантии объекта

Право подтверждать изменения принадлежит одному исполнителю и проверяется при фиксации. После сбоя ID, тип, версия и подтверждённые данные сохраняются. Новая нода загружает код и данные; инициализация успешно созданного объекта не выполняется повторно.

Неподтверждённый вызов клиент или SDK повторяет с прежним `request_id`. Метод до фиксации может выполняться несколько раз, но завершённая операция не применяется повторно. Это гарантия состояния и результата внутри Duro; она не распространяется на произвольные внешние действия.

Чтение возвращает полностью подтверждённое текущее состояние. Во время отказа допустима временная недоступность, но не выдача устаревшего кеша за текущее состояние. Техническая ревизия нужна для контроля конкурентных изменений; API чтения прошлых ревизий нет.

## Highload и приёмка

Сравниваем один, два и четыре исполнителя, равномерную и неравномерную популярность, смену горячих объектов, перегрузку и отказ при продолжающейся нагрузке. Учитываем стоимость долговечной записи и восстановления.

До сравнительных прогонов команда фиксирует оборудование, размеры данных, целевые RPS и p99 и допустимую долю технических ошибок. Эти цели и обязательный рост пропускной способности вычислительного профиля при увеличении пула входят в приёмку по [NFR-05](requirements/nonfunctional/NFR-05.md). Приложить только результаты низкой равномерной нагрузки недостаточно.

Демо использует аукцион и квоту. Генератор создаёт основную нагрузку, клиент показывает предметный результат, Grafana — состояние кластера. Проверяются сохранность подтверждённых операций, повторы, перенос и восстановление. Падение рабочей ноды и переключение primary БД проверяются отдельно, затем — отказ одной VM в полном стенде.

## Границы

Одно доверенное приложение, один язык обработчиков, один формат пакета, один регион. Код и данные сохраняются в PostgreSQL. Хранение работает через Patroni с синхронной репликацией; управление кластером использует etcd. Условия отказоустойчивости заданы в [NFR-02](requirements/nonfunctional/NFR-02.md).

В MVP не входят:

- ветвление объектов, пользовательская история, чтение прошлых ревизий и откаты;
- CRDT, локальные реплики и офлайн-редактирование;
- миграция кода уже созданных объектов;
- SQL API, транзакции и вызовы между объектами;
- сохранение памяти V8 или продолжение стека незавершённого метода;
- внешние действия, долговечная очередь команд и таймеры;
- недоверенные приложения и многопользовательская изоляция;
- геораспределение, автоматическое создание VM и шардирование БД;
- удаление объектов и выборочная очистка сохранённых результатов запросов.

Кеши и очереди ограничиваются. Долговечные данные MVP сохраняются до явной очистки стенда оператором; расход диска включается в нагрузочный отчёт. Для длительной эксплуатации понадобится отдельная политика хранения результатов.
