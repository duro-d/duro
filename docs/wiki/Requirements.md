# Требования к Duro

Duro предоставляет объекты с постоянным ID, исполняемым кодом и собственными данными. Разработчик загружает код, создаёт объект и вызывает его методы с JSON-аргументами. Duro организует исполнение, фиксацию данных, возврат результата и историю объекта.

MVP служит PoC. На нём проверяем вызовы по ID, работу с историей и независимыми ветками, а также восстановление после отказа исполнителя.

## Основной сценарий и модули

1. Разработчик загружает пакет кода через `registerType`: тип, версия, манифест и исполняемый код. Один пакет может использоваться многими объектами.
2. Клиент вызывает `create` с новым `object_id`, типом, версией и начальным аргументом. Duro запускает инициализацию и сохраняет объект как ревизию `0`.
3. Клиент вызывает `invoke` по ID объекта, передаёт имя метода, JSON-аргумент и `request_id`. Получает `{ result, revision }` после фиксации. Если метод не возвращает значение, `result` равен `null`; подтверждение выполнения всё равно приходит.

Регистрация пакета и создание объекта – два шага подключения приложения. Вызов неизвестного ID не создаёт объект автоматически. В MVP все методы вызываются с ожиданием результата или подтверждения; отдельной очереди фоновых заданий нет.

| Модуль | Ответственность |
| --- | --- |
| Маршрутизация | Публичный API, приём пакетов, выбор исполнителя, маршруты и восстановление обслуживания |
| Исполнение | Загрузка кода в runtime, очередь объекта, запуск метода и подготовка записей |
| Хранение состояния и истории | Пакеты кода, данные, журнал ревизий, результаты запросов и проверка владения |

Внутренние обращения между модулями выполняет Duro. Клиенту не нужны адрес исполнителя, поколение владельца или доступ к БД. Протокол описан в [архитектуре MVP](Architecture-MVP.md).

## Что входит в MVP

- Регистрация типов объектов и версий их кода.
- Создание объекта с начальным состоянием.
- Получение сведений об объекте и списка его методов.
- RPC-вызов метода по имени с JSON-аргументом.
- Чтение текущих данных и истории.
- Чтение данных выбранной ревизии.
- Создание независимой ветки из выбранной ревизии.
- Восстановление объекта после остановки исполнителя.
- Проверка состояния компонентов.

Обязательны требования с FR-01 по FR-08, а также FR-11 и FR-12. Откат по FR-09 является дополнительной операцией. Обновление кода с миграцией по FR-10 не входит в MVP. Дополнительные операции не входят в условия готовности PoC; при реализации они должны соблюдать общие гарантии.

Корректность сохранения, повторы и восстановление проверяются обязательно. Целевые задержки из NFR-05 служат ориентирами для замеров. Примеры вызовов приведены для клиентской библиотеки на JavaScript. API передаёт данные по HTTP в формате JSON.

## Отличительные возможности

Duro объединяет работу с объектом и его историей в одном API. Приложение читает прошлую версию без изменения текущих данных и создаёт из неё отдельный объект. Эти операции работают и при локальном развёртывании. Дополнительная операция отката возвращает прежние данные новой ревизией.

Cloudflare также предоставляет восстановление прошлых данных через PITR. Сравнение его интерфейса с операциями Duro приведено на странице [сравнения Durable Objects и Duro](durable-objects/Durable-Objects-and-Duro.md). Требования не включают превосходство над Cloudflare по скорости, стоимости или доступности.

## Основные понятия

| Понятие | Значение |
| --- | --- |
| Объект | Сущность с уникальным в развёртывании `object_id`, типом, версией кода и собственными данными |
| Тип | Описание инициализации и доступных RPC-методов |
| Версия кода | Зарегистрированный набор реализаций одного типа; изменение кода требует нового номера версии |
| Экземпляр | Код объекта и временные поля в памяти исполнителя |
| Хранилище объекта | Key-value данные, которые метод читает через `storage.get` и меняет через `storage.put` и `storage.delete`; ключи являются строками, значения имеют формат JSON |
| Ревизия | Номер сохранённого состояния данных и версии кода объекта; начинается с `0` и растёт на единицу |
| `request_id` | ID одной операции, который клиент сохраняет при её повторной отправке; защищает от повторного применения изменения |
| История | Начальные данные и сохранённые изменения с номерами ревизий |
| Ветка | Новый объект из выбранной ревизии другого объекта; имеет собственные ID и историю |
| Исполнитель | Процесс, который запускает методы объекта |

Метод сохраняет данные только через `storage`. Поля экземпляра автоматически не сохраняются. Чтение не создаёт ревизию. Успешный метод с записями создаёт одну ревизию, даже если записывает прежнее значение. Дополнительные операции отката и обновления кода также создают по одной ревизии.

Вызовы одного объекта выполняются по очереди. Duro не сравнивает прочитанную клиентом ревизию с текущей перед вызовом. Метод проверяет правила приложения на данных, доступных в момент его выполнения.

Для создания, RPC-вызова и ветвления клиент передаёт `request_id` отдельно от JSON-аргумента метода. Это правило действует и для дополнительных операций отката и обновления кода. Если ответ потерян, запрос отправляется с прежним ID и прежними параметрами. Duro возвращает сохранённый результат и не применяет завершённую операцию повторно. Новое действие получает новый ID. Правила заданы в разделе [«Общие правила»](Functional-Requirements.md#общие-правила), пример приведён в разделе [«Повтор запроса»](concepts/Concepts-Commands.md#повтор-запроса).

## Участники

| Участник | Действия |
| --- | --- |
| Разработчик приложения | Описывает типы и методы, собирает и загружает пакеты кода |
| Клиентское приложение | Обращается к API, передаёт JSON-аргументы, сохраняет `request_id` для повторов и показывает результаты пользователю |
| Оператор | Развёртывает компоненты, регистрирует код, настраивает доступ и следит за работой сервиса |

Проверка бюджета, выбор варианта плана и права пользователей приложения относятся к коду приложения. Duro отвечает за выполнение методов и сохранение данных.

## Границы MVP

Одно развёртывание обслуживает одно доверенное приложение. Разработчик упаковывает обработчики на одном документированном языке и загружает пакет через API. Duro сохраняет пакет, а исполнители получают нужную версию и запускают её в поддерживаемой среде исполнения. Подключение типа не требует пересборки или перезапуска серверов. Языки реализации серверных компонентов могут различаться. Версия кода объекта фиксируется при создании; ветка наследует версию выбранной ревизии.

Хранилище объектов в MVP предоставляет только key-value API: `storage.get`, `storage.put` и `storage.delete`. В этом API нет SQL-запросов, таблиц и управления схемой БД. История содержит сохранённые значения и удаления ключей.

Для демонстрации используются два исполнителя и готовая транзакционная БД с постоянным хранилищем. Требования определяют гарантии атомарности и сохранности; для PoC в архитектуре выбран PostgreSQL 18. Проверяем остановку одного исполнителя и возвращение прежнего владельца при доступных остальных компонентах. Достаточно запускаемого скрипта или CLI с примером поездки; отдельный пользовательский интерфейс не требуется.

В MVP не входят:

- CRDT, офлайн-редактирование и автоматическое слияние веток;
- SQL API для прикладного кода;
- транзакции нескольких объектов и копирование графа объектов;
- сохранение памяти процесса и продолжение метода с места остановки;
- таймеры и гарантированная доставка внешних действий;
- запуск недоверенного кода и изоляция разных приложений;
- геораспределение, автоматическое масштабирование и восстановление после потери диска или БД;
- удаление объектов и выборочная очистка истории.

В MVP также не входят обновление кода существующих объектов с миграциями и квоты общего объёма истории и результатов запросов по объектам. Доступное место в БД контролирует оператор.

Логические снимки разрешены как способ ускорить восстановление. Они не меняют API и не обязательны для первой реализации.

## Приёмка

Проверяются обязательные операции и сценарии, нагрузка и остановки исполнителей. Основным примером служит план поездки. Счётчик с ограничением подключается как второй тип без изменений ядра Duro. Отчёт содержит результаты проверок, исходные замеры и отклонения от целевых задержек. Если реализован откат, он проверяется отдельно по FR-09 и UC-06.
