## Общие правила

### Хранилище и завершение метода

В MVP интерфейс `storage` ограничен key-value операциями. `storage.get(key)`, `storage.put(key, value)` и `storage.delete(key)` работают только с данными текущего объекта. SQL-запросы, таблицы и управление схемой через этот интерфейс недоступны. Ключи хранятся как строки, значения имеют формат JSON. Отсутствующий ключ отличается от значения `null`; способ обозначения отсутствия документируется для языка обработчиков. Метод видит собственные подготовленные записи и удаления. Изменение полей экземпляра или прочитанного значения без `put` не сохраняет данные.

Каждый RPC-вызов получает один JSON-аргумент; отсутствие входных данных обозначается `null`. Метод может вернуть JSON-значение или завершиться без значения: исполнитель нормализует отсутствие результата в `null`. В обоих случаях успешный ответ содержит `{ result, revision }` и подтверждает фиксацию. Если обработчик асинхронный, исполнитель ждёт его завершения; неподдерживаемый результат или ошибка его сериализации считаются внутренней ошибкой и не приводят к частичным записям. Отправка команды без ожидания подтверждения и выполнение фоновых задач не входят в MVP.

Duro возвращает успешный ответ после долговечного сохранения данных, истории и результата запроса одной транзакцией. Для команды без записей сохраняется только результат без новой ревизии. При предметном отказе Duro отбрасывает подготовленные записи и запоминает отказ как завершённый результат без новой ревизии. Отказ инициализации запоминается без создания объекта.

При внутреннем исключении или таймауте выполнения обработчика подготовленные записи отбрасываются. Следующий метод получает подтверждённые данные; изменённую рабочую память исполнитель сбрасывает или пересоздаёт экземпляр. Гарантии относятся к хранилищу объекта и результату запроса. Внешние действия обработчика в эту транзакцию не входят.

### Повторы

Клиент задаёт `request_id` для создания, RPC-вызова и ветвления, а также для дополнительных операций отката и обновления кода. Область ID: `(object_id, request_id)`; при ветвлении используется целевой ID. Результат связан с видом операции и всеми её входными параметрами. Порядок полей JSON-объекта не влияет на сравнение, порядок элементов массива влияет.

При повторе Duro возвращает сохранённый ответ и его ревизию до проверки текущего состояния и версии кода. Другое содержимое под тем же ID получает `REQUEST_ID_CONFLICT`. Одновременные повторы не приводят к двум фиксациям. Метод до фиксации может выполняться повторно. Для нового действия клиент создаёт новый ID.

Предметные отказы и успешные RPC-вызовы без записей также запоминаются. Ошибки проверки запроса и технические ошибки сами по себе не становятся завершённым прикладным результатом. Если исход фиксации неизвестен, операция уже могла сохраниться. Клиент повторяет её с прежним ID и параметрами. Таймаут ожидания ответа не подтверждает отмену операции.

### Ошибки

Ответ с ошибкой содержит машинный `code` и сообщение. Для завершённого прикладного результата также возвращается ревизия; у отказа создания она отсутствует. Для PoC достаточно следующих кодов:

| Код | HTTP | Значение |
| --- | --- | --- |
| `INVALID_ARGUMENT` | 400 | Некорректный запрос или неподдерживаемые параметры |
| `UNAUTHORIZED` | 401 | Нет действительного токена |
| `NOT_FOUND` | 404 | Не найдены объект, тип, версия, метод или ревизия; сообщение указывает ресурс |
| `OBJECT_ALREADY_EXISTS` | 409 | ID объекта занят другим созданием |
| `CODE_VERSION_CONFLICT` | 409 | Тип и версия уже зарегистрированы с другими кодом или манифестом |
| `REQUEST_ID_CONFLICT` | 409 | ID запроса уже связан с другим содержимым |
| `DOMAIN_REJECTED` | 422 | Прикладной обработчик отклонил операцию |
| `LIMIT_EXCEEDED` | 413 | Превышен допустимый размер данных |
| `OVERLOADED` | 503 | Заполнена очередь |
| `UNAVAILABLE` | 503 | Недоступны БД, исполнитель или пакет кода |
| `EXECUTION_TIMEOUT` | 504 | Истекло время выполнения обработчика |
| `INTERNAL_ERROR` | 500 | Внутренняя ошибка исполнения |

Другая версия кода не подставляется вместо недоступной. Исправленный запрос получает новый `request_id`. После `OVERLOADED`, `UNAVAILABLE`, `EXECUTION_TIMEOUT`, `INTERNAL_ERROR` или потери ответа клиент может повторить прежний запрос с тем же ID. Внутренние исключения не раскрывают стек вызовов или секреты и не выдаются за предметный отказ.

При регистрации пакета неверный манифест, хеш, формат или неподдерживаемый runtime дают `INVALID_ARGUMENT`; другое содержимое под занятой парой «тип, версия» – `CODE_VERSION_CONFLICT` (HTTP 409). Отсутствие доступного исполнителя для проверки пакета или недоступность хранения дают `UNAVAILABLE`.
