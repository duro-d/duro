# FR-01. Зарегистрировать тип и версию кода

Раздел: [Функциональные требования](../../Functional-Requirements.md). Операция подчиняется [общим правилам](../../Functional-Requirements.md#общие-правила).

**Участник:** разработчик приложения или оператор.

**Вход:** исполняемый код и манифест с названием типа, версией, средой исполнения, точкой входа, списком RPC-методов и хешем кода. Хеш вычисляется по байтам исполняемого bundle; сам манифест в него не входит.

**Результат:** тип и версия доступны для создания объектов; Duro возвращает список зарегистрированных RPC-методов. Регистрация пакета сама не создаёт объект и не запускает инициализацию.

**Порядок выполнения:**

1. Разработчик собирает пакет и загружает его через API Duro. Для подключения типа не нужны пересборка или перезапуск серверов.
2. Duro проверяет манифест, хеш, поддержку среды исполнения, загрузку пакета и наличие функции инициализации и объявленных RPC-методов. Прикладная инициализация и RPC-методы при проверке не вызываются.
3. У каждого RPC-метода один JSON-аргумент и JSON-результат либо отсутствие значения, нормализуемое в `null`. Имена методов уникальны в пределах версии типа.
4. Duro атомарно сохраняет код и манифест под парой «тип, версия». Успешный ответ означает, что пакет доступен для загрузки любым совместимым исполнителем. Повтор с теми же кодом и манифестом возвращает регистрацию; другое содержимое под занятой парой получает `CODE_VERSION_CONFLICT`. Порядок полей JSON-манифеста на сравнение не влияет.

Для PoC достаточно одного документированного языка обработчиков, формата пакета и среды исполнения. Пакет загружается при работающем стенде; исполнители получают его по мере активации объектов. Версия существующего объекта остаётся прежней; её обновление с `migrate` описано в [FR-10](FR-10.md) за пределами MVP.

**Пример:** тип `TripPlan`, версия `1`, методы `addExpense`, `replaceExpensePrice` и `getSummary`.

**Приёмка:** два разных типа загружаются и вызываются без изменения образов или перезапуска исполнителей. Исполнитель с пустым кешем получает сохранённый пакет и активирует объект. Для каждой версии доступен точный список методов. Неподдерживаемый runtime, повреждённый пакет или отсутствие объявленных функций не приводят к успешной регистрации. Существующие объекты при регистрации нового пакета не меняются.
