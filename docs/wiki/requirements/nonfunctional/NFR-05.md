# NFR-05. Производительность

Раздел: [Нефункциональные требования](../../Nonfunctional-Requirements.md).

Сценарий и отчёт о замерах обязательны для PoC. Превышение целевых задержек записывается в отчёт и само по себе не блокирует приёмку. Потеря данных, повторное применение операции и нарушение атомарности остаются ошибками корректности при любой скорости.

Стенд: Linux, 4 логических CPU, 8 ГиБ RAM, SSD. Сохранение в БД должно быть долговечным; отключать его ради замеров нельзя. Генератор нагрузки работает на том же компьютере.

Перед проверкой создаются 100 объектов, у каждого до 32 КиБ данных и 100 ревизий. Нагрузка: 20 обращений в секунду, не более 10 одновременно; 80% – RPC-метод увеличения счётчика, 20% – чтение текущих данных. Обращения распределяются равномерно. Каждый новый RPC-вызов получает новый `request_id`. Метод меняет только ключ счётчика.

| Показатель | Цель |
| --- | --- |
| Продолжительность после прогрева 30 секунд | 60 секунд |
| p95 RPC-вызова | Не более 500 мс |
| p95 текущего чтения | Не более 500 мс |
| Неуспешные обращения без внесённых сбоев | 0 |
| p95 чтения ревизии и создания ветки | Не более 2 секунд для каждой операции |

Операции с историей проверяются отдельно, по 30 последовательных замеров. Источник содержит 100 ревизий и до 32 КиБ данных; выбирается ревизия `50`. Каждая ветка получает новый ID. Время считается от отправки до полного ответа. Подготовка данных не входит в замер.

Если реализован откат, для него проводятся те же 30 замеров с ориентиром p95 не более 2 секунд. Откаты выполняются на одной версии кода, каждый с новым `request_id`.

**Проверка:** сценарий нагрузки и исходные замеры прилагаются к отчёту. Указываются оборудование, версии и настройки. Для максимальных размеров [NFR-04](NFR-04.md) проверяется корректность; указанные задержки для них не требуются.
