# FoundationDB: детерминированная симуляция как способ проверки

Раздел: [Научная литература](Literature.md).

**Работа:** Zhou J., Xu M., Shraer A. и др. FoundationDB: A Distributed Unbundled Transactional Key Value Store. SIGMOD 2021, с. 2653–2666. [DOI: 10.1145/3448016.3457559](https://doi.org/10.1145/3448016.3457559), [текст статьи](https://www.foundationdb.org/files/fdb-paper.pdf) [[1]](#source-1).

**Направление Duro:** проверка корректности и поведения при отказах – [NFR-02](../requirements/nonfunctional/NFR-02.md) и [NFR-09](../requirements/nonfunctional/NFR-09.md).

**Зачем читать:** обязательные проверки MVP включают остановку исполнителя, запоздалую запись прежнего владельца и неопределённый исход фиксации. Работа описывает метод, которым такие сценарии проверяют воспроизводимо, а не однократным ручным экспериментом.

## О чём работа

FoundationDB – транзакционное key-value хранилище с разделённой архитектурой: управление конкурентностью, назначение версий и хранение данных разнесены по отдельным ролям, а не совмещены в каждом узле. Транзакции используют оптимистичное управление конкурентностью и многоверсионность.

Для Duro важнее вторая часть работы – способ разработки. Весь кластер запускается в одном процессе, а сеть, диски, время и планирование подменяются управляемыми реализациями. Симулятор вносит отказы: падения процессов, разделения сети, задержки, сбои дисков, перекосы часов. Любой найденный сценарий воспроизводится по начальному значению генератора случайных чисел. Для этого система написана на собственном расширении C++ с кооперативной многозадачностью, чтобы исполнение не зависело от планировщика операционной системы.

Отдельно описано восстановление: при отказе транзакционная система перезапускается целиком, поэтому путь восстановления один, а не набор частных случаев.

## Что применимо к Duro

| Приём | Применение в Duro |
| --- | --- |
| Кластер в одном процессе с подменой сети, времени и диска | Способ выполнить проверки [NFR-09](../requirements/nonfunctional/NFR-09.md) воспроизводимо и быстро |
| Воспроизведение сценария по начальному значению генератора | Найденное один раз нарушение становится регрессионной проверкой |
| Внесение отказов как часть обычного прогона тестов | Сценарии [NFR-02](../requirements/nonfunctional/NFR-02.md): остановка до сохранения и после сохранения до ответа |
| Одно общее восстановление вместо множества частных путей | Довод в пользу простого протокола смены владельца ([исполнение](../concepts/Concepts-Execution.md#владение)) |

## Границы применимости

Детерминированная симуляция требует, чтобы под неё был написан весь код: обращение к системному времени, к настоящей сети или к потокам операционной системы нарушает детерминизм. Для Duro это ограничение на устройство ядра, а не только выбор инструмента тестирования, и относится к архитектурному RFC. Сам [NFR-09](../requirements/nonfunctional/NFR-09.md) требует лишь запуска проверок одной командой и такого способа не предписывает.

Симуляция проверяет только те отказы, которые заложены в её модель, и только те нарушения, для которых сформулировано проверяющее условие. Замеры на реальном стенде из [NFR-05](../requirements/nonfunctional/NFR-05.md) она не заменяет.

Формулировка проверяющих условий – отдельная задача. Для аномалий изоляции её решает Elle [[2]](#source-2), выводя нарушения из журнала наблюдённых операций. Для Duro проверяемые свойства перечислены в [NFR-01](../requirements/nonfunctional/NFR-01.md) и [NFR-09](../requirements/nonfunctional/NFR-09.md).

## Рядом по теме

- Elle [[2]](#source-2) – инструмент проверки транзакций в Jepsen, который выявляет аномалии изоляции по наблюдённым историям операций.
- Анализ отказов из-за разделения сети в 25 распределённых системах [[3]](#source-3) – готовый набор сценариев для внесения отказов.
