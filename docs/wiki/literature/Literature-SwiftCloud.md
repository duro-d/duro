# SwiftCloud: причинно-согласованная клиентская реплика

Раздел: [Научная литература](Literature.md).

**Работа:** Zawirski M., Preguiça N., Duarte S., Bieniusa A., Balegas V., Shapiro M. Write Fast, Read in the Past: Causal Consistency for Client-Side Applications. Middleware 2015, с. 75–87. [DOI: 10.1145/2814576.2814733](https://doi.org/10.1145/2814576.2814733) [[1]](#source-1).

**Направление Duro:** локальная реплика объекта и её синхронизация с серверной стороной. Вне MVP.

**Зачем читать:** постановка задачи в работе почти совпадает с тем, что [Vision](../Vision.md) описывает для совместной работы: реплика на устройстве, собственные правки видны сразу, после подключения правки синхронизируются, а обслуживающий узел может измениться.

## О чём работа

SwiftCloud держит на клиенте частичную реплику базы CRDT-объектов. Клиент применяет свои изменения локально и немедленно, затем передаёт их узлу центра обработки данных. Чтения выполняются из причинно-согласованного снимка.

Основная трудность – метаданные зависимостей. Если клиент зависит от изменений, принятых только одним узлом, то при переключении на другой узел его зависимости окажутся невыполнимыми. Решение дало работе название: клиент читает «из прошлого» – снимок, уже принятый достаточным числом узлов, – и за счёт этого переключается без блокировки. Собственные изменения клиент видит сразу, поверх такого снимка. Метаданные привязаны к узлам, а не к отдельным клиентам, поэтому их объём не растёт с числом клиентов.

Цена решения названа прямо: чтения возвращают немного устаревшие данные.

## Что применимо к Duro

| Решение | Отношение к модели Duro |
| --- | --- |
| Своя правка применяется локально сразу, распространяется асинхронно | Будущий офлайн-режим из Vision |
| Чтение из устойчиво принятого снимка вместо самых свежих данных | Другое требование, чем сейчас: [NFR-01](../requirements/nonfunctional/NFR-01.md) не допускает выдавать старый кеш за текущие данные |
| Переключение обслуживающего узла без повторного применения изменений | Та же задача, что `request_id` в [контракте команд](../concepts/Concepts-Commands.md#повтор-запроса) |
| Метаданные привязаны к узлам, а не к клиентам | Ориентир по стоимости синхронизации при росте числа устройств |

Главный вывод для планирования: вводя реплики, придётся выбрать между свежестью чтения и возможностью сменить узел без блокировки. Сейчас Duro выбирает свежесть, и это решение зафиксировано в [NFR-01](../requirements/nonfunctional/NFR-01.md).

## Границы применимости

Все операции в SwiftCloud – операции CRDT: сходимость обеспечивает тип данных. Операций, требующих общего решения, например бронирования или проверки бюджета, в модели нет. Для Duro это значит, что клиентской репликой одна задача не закрывается; потребуется деление операций по критерию из [RedBlue consistency](Literature-RedBlue.md).

История ревизий и ветки в работе не рассматриваются. Снимок нужен для согласованного чтения, а не для возврата пользователя к прошлой версии по запросу.

## Рядом по теме

- COPS [[2]](#source-2) – исходная постановка масштабируемой причинной согласованности для гео-хранилища.
- Delta-state CRDT [[3]](#source-3) – обмен дельтами вместо полного состояния: ориентир по объёму трафика синхронизации.
