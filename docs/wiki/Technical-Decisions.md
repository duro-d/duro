# Технические решения MVP

Эта страница фиксирует решения, необходимые для совместной разработки MVP. Контракт объекта и гарантии общие для команды. Внутренние алгоритмы, схемы таблиц и организация потоков уточняются в архитектуре каждого модуля.

## На чём работает система

| Часть | Решение |
| --- | --- |
| Маршрутизация и размещение | Go |
| Рабочие ноды | Rust, Tokio; V8 через `deno_core` и его зависимость `rusty_v8` |
| Модуль состояния | Язык выбирает его автор; совместимость определяется gRPC-контрактом |
| Пользовательские обработчики | JavaScript, один самодостаточный ES module bundle |
| Внешний API | HTTP/JSON и небольшой клиентский SDK |
| Между модулями | gRPC/Protobuf |
| Долговечные данные | PostgreSQL 18 |
| Отказоустойчивость БД | Patroni, синхронная репликация в строгом режиме |
| Координация кластера | etcd |
| Метрики и нагрузка | Prometheus, Grafana, k6 |
| Запуск | Docker Compose локально; несколько VM для испытаний отказа узла |

## Почему JavaScript и V8

Для MVP выбираем JavaScript на V8. V8 используется в Cloudflare Workers, на котором основана модель Durable Objects. Это подходящий ориентир, но не обязательный стандарт всех объектных платформ. [Устройство Workers](https://developers.cloudflare.com/workers/reference/how-workers-works/).

В Rust используем `deno_core`: он предоставляет `JsRuntime`, загрузку модулей, цикл событий и подключение функций Rust к JavaScript. Связь с V8 обеспечивает `rusty_v8`. Это готовая основа исполнения; SDK Duro, очереди, Storage API и фиксацию реализует команда. Сам `deno_core` не предоставляет полный Deno, Node.js или поддержку TypeScript. [README deno_core](https://github.com/denoland/deno/blob/main/libs/core/README.md), [rusty_v8](https://github.com/denoland/rusty_v8).

Обработчики пишутся на JavaScript либо заранее собираются из TypeScript в JavaScript. На сервер загружается готовый bundle с зависимостями внутри; скачивания npm-пакетов и компиляции TypeScript на рабочей ноде нет. Версии Rust, V8 и библиотек закрепляются при создании первого запускаемого стенда.

## Как загружается код

Пакет состоит из JavaScript bundle и манифеста: тип, версия, runtime `javascript-v8`, формат `esm`, список методов и SHA-256 bundle. Модуль экспортирует `init(ctx, input)` и объект `methods` с именованными функциями `(ctx, argument)`.

`registerType` проверяет пакет через исполнитель и сохраняет его в модуле состояния. В MVP код и манифест хранятся в PostgreSQL; отдельное хранилище артефактов не требуется. `create` связывает ID с типом и версией. Исполнитель получает пакет при активации и кеширует по типу, версии и хешу. Регистрация нового пакета не требует пересборки рабочих нод.

Версия существующего объекта фиксирована. Обновление с миграцией состояния отложено. Пример пакета приведён в [аукционе](concepts/Concepts-Auction.md).

## Как сохраняется состояние

Прикладной код работает с `ctx.storage`:

| Операция | Поведение |
| --- | --- |
| `await storage.get(key)` | Возвращает JSON-значение или `undefined`, если ключ отсутствует |
| `await storage.put(key, value)` | Подготавливает запись JSON-значения |
| `await storage.delete(key)` | Подготавливает удаление ключа; отсутствие ключа допустимо |

Доступ ограничен текущим объектом. Метод видит собственные подготовленные записи. Полученные значения копируются; изменение JavaScript-объекта без `put` ничего не сохраняет. `put` подтверждает помещение в буфер, а не долговечную запись в БД.

После успешного завершения метода исполнитель передаёт изменения и результат модулю состояния. Тот одной транзакцией проверяет владельца, сохраняет записи и результат по `request_id`. Только после долговечного подтверждения возвращается успех клиенту. Явный `commit` и отдельный API транзакций приложению не нужны: граница транзакции – один вызов метода одного объекта.

При исключении, таймауте или ошибке сериализации буфер отбрасывается. `ctx.reject(message)` завершает метод предметным отказом: записи отбрасываются, отказ сохраняется для повторов. Подробнее – [команды и фиксация](concepts/Concepts-Commands.md).

Поля JavaScript, глобальные переменные, V8 heap и стек вызова долговечными не являются. Восстановление загружает текущие сохранённые данные. Event Sourcing с предметными событиями для этого не требуется.

## Почему PostgreSQL, а не Redis как основное хранение

Транзакция PostgreSQL позволяет сохранить состояние, результат запроса и проверить владение одной операцией. Текущие данные хранятся как KV с JSON-значениями; физическую схему выбирает модуль состояния. SQL из обработчиков недоступен.

Redis Cluster использует асинхронную репликацию и допускает потерю подтверждённых записей при отказах. Поэтому он не выбран основой контракта сохранности Duro. Redis не является обязательной зависимостью MVP: кеши маршрутов, пакетов и активных объектов находятся в памяти соответствующих модулей. [Спецификация Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

Для испытаний отказа узла хранения используем три PostgreSQL-инстанса и Patroni с `synchronous_mode` и `synchronous_mode_strict`. Успех операции должен означать подтверждённую синхронную фиксацию. Без подходящей реплики запись приостанавливается; принудительное переключение с потерей данных в приёмку не входит. Неопределённый результат commit и его повтор проверяются отдельно. [Режимы репликации Patroni](https://patroni.readthedocs.io/en/latest/replication_modes.html).

Реплики повышают доступность и сохранность. Запись по-прежнему ограничена primary. Измеряем этот предел; шардирование БД и переход на распределённую SQL-БД не входят в MVP.

## Для чего etcd

etcd хранит сведения о доступных рабочих нодах, помогает выбрать активный контроллер размещения и служит координатором Patroni. Запросы к объектам не проходят через etcd; маршрутизаторы используют кеш маршрутов.

Авторитетные назначения объектов, поколения владельцев и аренды хранятся в PostgreSQL через модуль состояния. Размещение выбирает модуль маршрутизации; разрешение на запись проверяет модуль состояния в транзакции. Исчезновение записи ноды из etcd само по себе не даёт другому исполнителю право писать. [Гарантии etcd](https://etcd.io/docs/v3.6/learning/api_guarantees/).

## Какие возможности среды доступны

MVP обслуживает одно доверенное приложение. Помимо стандартного JavaScript, runtime предоставляет только контекст Duro: `objectId`, `storage` и `reject`. Сеть, файловая система, фоновые задачи, таймеры и вызовы других объектов из обработчика не предоставляются. Асинхронные методы и `await storage.*` поддерживаются; платформа ждёт завершения возвращённого Promise.

## Что решается внутри модулей

В архитектурах модулей будут описаны организация потоков и V8 isolates, структура очередей и кешей, таблицы и индексы БД, конкретные сообщения gRPC и коэффициенты алгоритмов размещения. Эти решения должны соблюдать общий контракт и проверяться на highload-стенде. Выбор языка модуля состояния не меняет внешний API.
