# Команды и фиксация

Команда вызывает метод объекта. Метод читает и записывает данные через `storage`; Duro связывает принятые записи с ревизией и результатом запроса.

## Исполнение метода

Концептуальный контракт прикладного кода:

```text
initialize(context, input) -> response | domain_error
method(context, argument_json) -> response | domain_error
```

Через `context.storage` разработчик обращается к хранилищу текущего объекта. Вызовы `put` и `delete` подготавливают записи в транзакционной области команды. Исполнитель ждёт завершения обработчика, включая асинхронный, и проверяет сериализацию результата до фиксации. Отсутствие возвращаемого значения нормализуется в JSON `null`; клиент всё равно получает `{ result, revision }` после фиксации.

Возвращать массив предметных событий или описывать отдельный `apply` для этой модели не требуется. Различие между журналом хранилища и предметными событиями разобрано в [модели хранения](Concepts-Persistence.md).

## Этапы выполнения команды

1. Duro проверяет сохранённый результат для `(object_id, request_id)` до выбора исполнителя и проверки текущей версии кода. Завершённый повтор возвращает этот результат.
2. Для нового запроса находит объект и владельца, ставит вызов в очередь. Перед запуском повторно проверяет результат запроса, затем загружает код и подтверждённые данные.
3. Метод выполняет предметные проверки и подготавливает записи в `storage`.
4. Duro проверяет полномочия исполнителя и фиксирует журнал, текущие данные и результат запроса.
5. Клиент получает ответ с ревизией, к которой относится результат.

Это логический порядок. Распределение проверок между маршрутизатором, исполнителем и хранением описано в [архитектуре MVP](../Architecture-MVP.md).

При отказе записи команды отбрасываются. Частично изменённая рабочая память также не должна стать основанием следующего метода: экземпляр нужно привести к подтверждённым данным или пересоздать.

## Ревизия

Ревизии нумеруются так:

- создание вместе с начальными записями задаёт ревизию `0`;
- успешная команда с записями `put` или `delete` создаёт одну новую ревизию;
- чтение, команда без записей и предметный отказ сохраняют текущую ревизию;
- дополнительные операции отката данных и обновления кода создают новую ревизию.

Несколько записей одной команды входят в одну границу фиксации. Частично применённая команда не образует доступную версию.

Успешная команда с `put` или `delete` создаёт новую ревизию, даже если итоговые данные совпадают с прежними. Поэтому разные ревизии могут содержать одинаковые пользовательские данные. Удаление таких записей и сжатие промежуточных операций пока не входят в публичный контракт.

Для команды без записей Duro также запоминает завершённый результат. Служебная запись для повторов не меняет ревизию пользовательских данных.

## Повтор запроса

`request_id` – уникальная строка, которой клиент обозначает одну операцию. Например, это UUID. Она нужна на случай потери ответа: данные уже могли сохраниться, и повтор не должен применить изменение второй раз.

Клиент создаёт ID до отправки и сохраняет его при всех повторах той же операции. Для нового действия создаёт новый ID, даже если имя метода и аргумент совпадают. Поле передаётся отдельно от JSON-аргумента метода и не является частью данных приложения. Его область: `(object_id, request_id)`. Для создания ветки используется ID создаваемого объекта.

Duro связывает завершённый результат с видом операции и её содержимым. Для RPC это имя метода и JSON-аргумент. Тот же запрос получает сохранённые ответ и ревизию. Если ID уже связан с другим содержимым, запрос отклоняется.

Сохранённый результат проверяется до запуска метода и проверки текущей версии кода. Это правило действует и после обновления кода при реализации этой операции.

```javascript
await duro.invoke("trip/main", "addExpense", { id: "activity", amount: 100 }, {
    request_id: "main-activity",
});
// → записи зафиксированы как revision=3; ответ потерян

await duro.invoke("trip/main", "addExpense", { id: "activity", amount: 100 }, {
    request_id: "main-activity",
});
// → прежний ответ с revision=3; новых записей нет
```

Результат описывает исходную команду. Текущие данные могли измениться после неё; для них нужен отдельный запрос чтения.

Потеря ответа не сообщает клиенту исход фиксации. Повтор с прежним ID позволяет проверить сохранённый результат. Метод до фиксации может выполняться повторно. Результаты хранятся до полной очистки данных развёртывания, как задано в [NFR-03](../requirements/nonfunctional/NFR-03.md).

Предметный отказ входит в завершённый результат команды, а её подготовленные записи отбрасываются. Если запрос не прошёл проверку входных данных, метод не выполняется. Исправленное намерение получает новый ID запроса.

## Конкурентные изменения

В MVP все RPC-вызовы одного объекта проходят через общую очередь, в том числе методы без записей. Время отправки на клиенте не задаёт общий порядок конкурентных запросов. Прямые операции `read`, `describe` и чтения истории обращаются к подтверждённым данным без запуска методов.

Клиент не передаёт ожидаемую ревизию. Метод проверяет данные, актуальные на момент его выполнения.

Предметные условия проверяет метод. Например, проверка бюджета учитывает весь список расходов в транзакционной области команды. Duro не знает, что означает превышение бюджета.

## Чтение данных

```text
read(object_id)            -> { data, revision, code_version }
readRevision(object_id, 2)  -> { data, revision=2, code_version }
```

В эскизе `data` обозначает содержимое хранилища объекта. Это не дамп полей экземпляра. Версия кода возвращается вместе с данными; тип и происхождение ветки доступны через `describe`.

`read` запрашивает подтверждённые текущие данные. Если команда завершилась до начала чтения, чтение видит её записи или более позднюю ревизию, в том числе после смены исполнителя.

Чтение по номеру возвращает конкретную версию данных и не меняет текущий объект. Прикладные показатели, например общую стоимость плана, приложение рассчитывает по прочитанным значениям. Произвольные методы чтения над историческим экземпляром пока не входят в необходимый API.
