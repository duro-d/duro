# Исполнение и восстановление

Объект сохраняет ID и явно записанные данные, когда его экземпляр в памяти прекращает работу. Исполнитель создаёт новый экземпляр прикладного кода и предоставляет ему доступ к подтверждённому хранилищу.

## Создание экземпляра

Активация существующего объекта отличается от его первоначального создания. Начальные пользовательские значения записываются один раз при создании объекта. При последующих активациях код читает уже сохранённые данные.

Duro может использовать текущее материализованное содержимое хранилища или восстановить его по журналу и логическому снимку. Этот выбор не меняет адрес объекта и смысл сохранённых версий.

Разработчик отвечает за загрузку нужных значений в поля экземпляра и за согласованность своих кешей с `storage`. Обычные поля не становятся долговечными. После отката данных или смены кода Duro пересоздаёт экземпляр.

## Владение

В предлагаемой модели один исполнитель имеет право подтверждать изменения объекта. После его отказа Duro передаёт это право другому исполнителю.

Старый процесс может продолжить работу после паузы или потери связи, пока новый уже обслуживает объект. Его старые полномочия не позволяют сохранить результат и изменения. На пути фиксации нужна проверка актуальных полномочий. Поколение владельца обозначает их смену и не заменяет ревизию данных.

Для PoC протокол выдачи и проверки полномочий описан в [архитектуре MVP](../Architecture-MVP.md): аренда и поколение хранятся в БД, а полномочия проверяются в транзакции фиксации. Причины, по которым истечения аренды недостаточно для безопасной записи, разобраны в [статье Мартина Клеппмана о распределённых блокировках](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html).

Прежний исполнитель также не должен выдавать устаревший кеш за текущие данные. Чтения выполняются с гарантиями [NFR-01](../requirements/nonfunctional/NFR-01.md).

## Восстановление данных и повтор метода

Duro восстанавливает содержимое `storage` по принятым изменениям. При этом не нужно заново вызывать методы, которые создали эти записи.

Например, если метод выбрал время или случайное значение и записал его, история содержит результат выбора. Восстановление применяет сохранённое значение. Повтор метода до успешной фиксации всё ещё может вычислить другой результат.

Выполнение незавершённого метода с места остановки не входит в модель. После перезапуска объект использует сохранённую версию кода без повторной инициализации. При реализации обновления кода перезапуск также не вызывает повторный `migrate`.

| Ситуация | Требуемое поведение |
| --- | --- |
| Исполнитель остановился до фиксации | Подготовленные записи не входят в подтверждённую версию; запрос можно повторить |
| Данные и результат зафиксированы, ответ потерян | Повтор получает сохранённый ответ без новых записей |
| Исход фиксации неизвестен | Duro проверяет подтверждённые данные и результат по ID запроса |
| Метод изменил память и завершился отказом | Его записи отбрасываются, а следующий вызов работает с подтверждёнными данными |
| Вернулся прежний владелец | Его старые полномочия не позволяют принять запись |

Это поведение предстоит проверить на реализации.

В PoC проверяется остановка одного исполнителя при доступной БД и остальных компонентах, а также запрет записи от прежнего владельца. Отказ узла с данными, управляющей части и полные сетевые разделения требуют отдельных сценариев и протоколов. Восстановление подтверждается успешным изменяющим RPC-вызовом на другом исполнителе по [NFR-02](../requirements/nonfunctional/NFR-02.md).

## Ограничения выполнения методов

Разработчик загружает доверенный пакет кода через API Duro. При активации исполнитель получает сохранённый пакет нужной версии, проверяет хеш и запускает его в поддерживаемой среде исполнения с API `storage`. Локальный кеш пакетов можно восстановить из хранения. Для PoC достаточно одного документированного языка и runtime; подключение типа не требует пересборки исполнителей. Доставка кода описана в [архитектуре MVP](../Architecture-MVP.md).

Лимиты времени, объёма записей и очереди заданы в [NFR-04](../requirements/nonfunctional/NFR-04.md). Отмена может быть кооперативной; после истечения срока поздний результат не сохраняется.

Фоновая работа и долговечные таймеры не нужны для примера плана поездки. Они потребуют сохранять намерения запуска и согласовывать доставку с состоянием объекта.

## Внешние действия

Транзакционная область метода охватывает хранилище объекта и служебный результат запроса. HTTP-вызов, отправка уведомления или покупка билета происходят во внешней системе и имеют собственный исход.

Для первого примера методы работают только с данными плана. Откат изменяет сохранённый план, а не внешние действия.

Доверенный процесс технически может обратиться к сети в обход контрактов Duro. Изоляция недоверенного кода ещё не спроектирована. Для управляемых внешних действий нужно отдельно определить доставку, повторы и правила исполнения в ветках.
