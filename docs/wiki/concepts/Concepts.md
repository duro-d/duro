# Концепции

Duro проектируется как инфраструктура для объектов с постоянным ID, поведением и собственным хранилищем. Разработчик явно читает и записывает данные в методах объекта. Платформа ведёт историю принятых изменений и предоставляет операции работы с версиями.

Это проектная модель, ещё не подтверждённая реализацией. Обязательные гарантии заданы в требованиях, а взаимодействие трёх модулей – в [архитектуре MVP](../Architecture-MVP.md). Их выполнение предстоит проверить на прототипе.

Обязательное поведение первой версии, границы гарантий и критерии приёмки сформулированы в [требованиях к MVP](../Requirements.md). PoC включает историю и ветки. Откат является дополнительной операцией; обновление кода с миграциями не входит в MVP. Приведённые здесь варианты развития не расширяют объём первой версии.

## Основная модель

Приложение загружает пакет кода типа через `registerType`, затем создаёт объекты этого типа через `create`. При создании ID связывается с типом и версией пакета. После этого клиент вызывает методы через `invoke`; маршрутизация, загрузка кода и фиксация выполняются внутри Duro.

В методе разработчик обращается к `storage`: читает значения, проверяет предметные правила и записывает изменения. Маршрутизатор выбирает исполнителя, исполнитель запускает код, модуль хранения сохраняет данные, историю, пакеты и результаты запросов.

В MVP хранилище объекта предоставляет только KV API с операциями `get`, `put` и `delete`. Ключи являются строками, значения имеют формат JSON. SQL API не входит в MVP. Duro фиксирует принятые записи в журнале вместе с результатом команды. По журналу можно восстановить содержимое хранилища на нужной ревизии.

Клиент вызывает метод по имени с одним JSON-аргументом и передаёт `request_id` отдельно от аргумента. После фиксации получает результат и ревизию; отсутствие возвращаемого значения обозначается `null`. В PoC версия кода фиксируется при создании объекта. Обновление кода вместе с преобразованием данных не входит в MVP.

Из выбранной версии можно создать независимую ветку с новым ID. Дополнительная операция отката принимает данные прошлой версии как новое изменение исходного объекта, сохраняя прежнюю историю.

## Разделение ответственности

| Приложение | Duro |
| --- | --- |
| Определяет методы и структуру данных | Адресует объект и организует исполнение |
| Выбирает, какие данные явно записать в `storage` | Сохраняет записи и их историю |
| Проверяет предметные ограничения | Организует последовательную обработку изменений объекта |
| Определяет смысл изменений и пользовательские ответы | Фиксирует результат команды и распознаёт повторы |
| Сравнивает варианты плана | Предоставляет историческое чтение и ветку; откат является дополнительной операцией |

Поля экземпляра остаются рабочей памятью. Duro не должна автоматически сохранять произвольные поля, стек вызовов или память процесса. Логические снимки содержимого `storage` могут ускорять восстановление; они описаны в [модели хранения](Concepts-Persistence.md).

## Журнал изменений и Event Sourcing

В текущем предложении журнал описывает принятые изменения хранимых данных: запись значения и удаление ключа. Это события уровня хранилища.

Предметные события вроде `ExpenseAdded` имеют другой смысл. Их определяет разработчик приложения. Операция `put("expenses", value)` сама по себе не сообщает платформе, почему изменился список расходов.

Поэтому в документации используем название «журнал изменений хранилища». Классический Event Sourcing с предметными событиями рассматриваем отдельно от выбранного способа явного сохранения данных.

## Термины

| Термин | Значение |
| --- | --- |
| Объект | Логическая сущность с ID, методами и собственными данными |
| Экземпляр | Загруженный прикладной код объекта и его рабочая память |
| Хранилище объекта | Пользовательские данные, явно записанные через `storage` |
| Команда | Вызов метода, который может изменить данные |
| Ревизия | Номер сохранённого состояния данных и версии кода |
| Журнал | Последовательность принятых изменений хранилища |
| Снимок | Образ хранимых данных на определённой ревизии |
| Ветка | Новый объект из выбранной версии данных другого объекта |
| Откат | Новая ревизия исходного объекта с данными выбранной прошлой версии |
| Владелец | Исполнитель, уполномоченный подтверждать изменения объекта |

CRDT, слияние веток и операции над несколькими объектами требуют дополнительных контрактов. Основания для их отсрочки приведены в [анализе альтернатив](Concepts-Alternatives.md).
