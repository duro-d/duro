# Пример: план поездки

Приложение помогает составить план поездки, уложиться в бюджет и сравнить варианты. В плане хранятся расходы на дорогу, жильё и занятия. Цены в примерах условные; приложение не покупает билеты и не бронирует жильё.

Такой пример показывает работу объекта, историю правок, независимую ветку и откат без симуляции движения или фонового расчёта.

## Модель объекта TripPlan

Объект `TripPlan` объединяет лимит бюджета и список расходов. У расхода есть ID и сумма; название можно хранить дополнительно. В примере суммы задаются неотрицательными целыми числами. Общую стоимость приложение вычисляет по сохранённым позициям.

Добавляя расход или меняя его стоимость, метод объекта проверяет бюджет. Проверка и запись относятся к одной команде, чтобы конкурентные правки не использовали один и тот же остаток.

Расходы входят в данные плана. Для них не нужны самостоятельные распределённые объекты. При создании ветки Duro переносит данные всего выбранного плана.

## Операции приложения

| Команда | Что проверяет и меняет метод объекта |
| --- | --- |
| `addExpense` | Добавляет позицию с новым ID, если итог укладывается в бюджет |
| `replaceExpensePrice` | Меняет сумму существующей позиции с проверкой бюджета |
| `getSummary` | Возвращает бюджет и итог расходов без записи новых данных |

Это методы пакета `TripPlan` версии `1` в примерах. Приложение определяет эти правила. Duro организует исполнение метода, фиксацию данных и истории, обработку повторов и доступ к версиям. Удаление расхода и изменение бюджета можно добавить как прикладные методы в следующем пакете; для демонстрации они не обязательны.

## Основной и альтернативный планы

Создаём `trip/main` с бюджетом 1000. Затем добавляем дорогу за 200 и жильё за 500. Получаем ревизию 2 с общей стоимостью 700.

Из этой ревизии создаём `trip/alternate`. В альтернативном плане меняем жильё на вариант за 350. В оба плана добавляем занятие за 100.

| Объект | Ревизия | Сохранённые расходы | Итого |
| --- | --- | --- | --- |
| Основной план | 0 | Пустой список | 0 |
| Основной план | 1 | Дорога: 200 | 200 |
| Основной план | 2 | Дорога: 200; жильё: 500 | 700 |
| Основной план | 3 | Дорога: 200; жильё: 500; занятие: 100 | 800 |
| Ветка из основной ревизии 2 | 0 | Дорога: 200; жильё: 500 | 700 |
| Альтернативный план | 1 | Дорога: 200; жильё: 350 | 550 |
| Альтернативный план | 2 | Дорога: 200; жильё: 350; занятие: 100 | 650 |

Одинаковая ревизия разных объектов не означает одинаковые данные. У ветки собственная последовательность изменений.

## Псевдокод вызовов

Псевдокод на JavaScript показывает смысл операций. `tripPlanPackage` обозначает собранный код с манифестом версии `1`; точные сигнатуры SDK ещё не выбраны.

```javascript
await duro.registerType(tripPlanPackage);
// Код сохранён и проверен; объекты пока не созданы.

await duro.create({
    object_id: "trip/main", type: "TripPlan", code_version: "1",
    input: { budget: 1000 }, request_id: "create-main",
});
// → revision=0

await duro.invoke("trip/main", "addExpense", { id: "train", amount: 200 }, {
    request_id: "add-train",
});
// → revision=1

await duro.invoke("trip/main", "addExpense", { id: "hotel", amount: 500 }, {
    request_id: "add-hotel",
});
// → revision=2

await duro.fork({
    source_object_id: "trip/main", source_revision: 2,
    target_object_id: "trip/alternate", request_id: "fork-alternate",
});
// → object_id="trip/alternate", revision=0

await duro.invoke("trip/main", "addExpense", { id: "activity", amount: 100 }, {
    request_id: "main-activity",
});
// → revision=3

await duro.invoke("trip/alternate", "replaceExpensePrice", { id: "hotel", amount: 350 }, {
    request_id: "alternate-hotel",
});
// → revision=1

await duro.invoke("trip/alternate", "addExpense", { id: "activity", amount: 100 }, {
    request_id: "alternate-activity",
});
// → revision=2
```

Для сравнения приложение читает обе версии и рассчитывает стоимость. Выбор варианта остаётся за пользователем.

## История и откат

Откат является дополнительной возможностью PoC. История и независимые варианты входят в обязательную демонстрацию.

Чтение `trip/main@2` покажет план стоимостью 700. Текущий основной план при этом останется на ревизии 3 со стоимостью 800.

Для отката предлагаем отдельную операцию `restore`: она принимает старую версию данных как новое изменение того же объекта. В примере восстановление данных ревизии 2 создаст ревизию 4 со стоимостью 700.

Ревизия 3 останется в истории. Альтернативный план сохранит собственные данные. Подробная семантика операций описана на странице [истории и веток](Concepts-History.md).

## Повторы и восстановление

Если ответ на `main-activity` потеряется после фиксации, повтор того же запроса вернёт результат ревизии 3. Вторая позиция расхода не появится.

Если затем выполнить откат до данных ревизии 2, сведения о завершённых запросах нужно сохранить. Запоздалый повтор `main-activity` вернёт прежний результат, сохранив текущие данные после отката. Чтобы добавить расход заново, клиент отправляет новую команду с новым ID.

После остановки исполнителя следующий запрос должен получить доступ к подтверждённым данным плана на другом исполнителе. Незавершённый метод можно выполнить заново с тем же ID запроса; исход уже зафиксированной команды определяется по сохранённому результату.

Эти примеры проверяют согласованность предлагаемого контракта. Испытания реализации при сбоях ещё предстоят.

## Оценка применимости Duro

Такое приложение можно написать как обычный сервис с БД. Для небольшого числа планов этот вариант может оказаться достаточным.

Пользу Duro нужно проверять по тому, какую работу разработчик сможет взять из платформы: адресацию объектов, сохранение истории, ветвление, откат и обработку повторов. При сравнении оба варианта должны поддерживать одинаковое поведение.

В PoC независимость ядра проверяет второй тип – счётчик с ограничением по NFR-09. Другие приложения можно исследовать позднее. Производительность и спрос на такой API пока не подтверждены.
