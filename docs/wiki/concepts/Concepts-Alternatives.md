# Альтернативы и проверка гипотезы

Рабочая гипотеза: разработчику будет полезен объектный API с явным сохранением данных, доступной историей, независимыми ветками и откатом. План поездки показывает этот контракт на знакомых данных.

Пользователь Duro здесь разрабатывает серверную часть приложения. Пользователь приложения редактирует план и сравнивает варианты.

Мы сверили возможности аналогов с документацией 9 октября 2026 года. Применимость к нашему сценарию оцениваем по этим контрактам. Реализаций для сравнения и замеров пока нет.

## Сравнение подходов

| Подход | Документированные возможности | Оценка для нашего сценария |
| --- | --- | --- |
| Сервис и PostgreSQL | Транзакции фиксируют группу изменений как одну операцию. [Документация](https://www.postgresql.org/docs/current/tutorial-transactions.html) | Можно хранить планы, версии и результаты запросов. Историю, ветвление и откат разработчик реализует под своё приложение |
| Cloudflare Durable Objects | Предоставляет явный Storage API; обычные поля экземпляра не сохраняются после выгрузки. [Хранилище](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/), [память](https://developers.cloudflare.com/durable-objects/reference/in-memory-state/) | Основной ориентир для интерфейса сохранения. Заимствуем разделение памяти и явно записанных данных; полный API и его детали не копируем |
| Cloudflare PITR | Возвращает БД объекта к выбранной точке при следующем перезапуске. [Storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) | Нужно сравнить с историческим чтением, созданием отдельного объекта и предлагаемым откатом новой ревизией |
| Akka Event Sourced Entities | Приложение формирует события; состояние восстанавливается их применением. [Документация](https://doc.akka.io/sdk/event-sourced-entities.html) | Ориентир для отдельного варианта с предметными событиями. Он предъявляет другие требования к прикладному коду, чем методы с `storage.put` |
| Restate Virtual Objects | Данные привязаны к ключу; один обработчик изменяет конкретный ключ, разные объекты могут исполняться параллельно. [Модель сервисов](https://docs.restate.dev/foundations/services) | Подходящая основа объектного исполнения. Пользовательскую историю и контракт альтернативных версий нужно сравнивать на одном сценарии |
| Temporal | Восстанавливает workflow по истории; Reset продолжает исполнение из выбранной точки и завершает текущее. [История](https://docs.temporal.io/encyclopedia/event-history), [контракт Reset](https://github.com/temporalio/api/blob/main/temporal/api/workflowservice/v1/service.proto) | Для независимых вариантов потребуется прикладной контракт. Reset отличается от предложенной ветки и отката данных |
| Automerge | Предоставляет историю, версии, fork и merge документа. [Документация](https://automerge.org/automerge-swift/documentation/automerge/changesandhistory/) | Подходит для совместных данных. Общую проверку бюджета и серверное принятие решений нужно определить отдельно |
| Rivet Actors | Предоставляет адресуемые объекты с состоянием и жизненным циклом. [Обзор](https://rivet.dev/actors/docs/) | Ориентир для удобства объектного API и развёртывания |
| Ветки БД Neon | Позволяют создавать независимые ветки Postgres из доступной истории. [Описание](https://neon.com/blog/practical-guide-to-database-branching) | Упрощают копирование окружения. Для Duro рассматриваем работу с версией данных одного адресуемого объекта |

Сравнение не утверждает, что у продуктов отсутствуют другие возможности. Для проверки нужен один и тот же сценарий с сопоставимыми условиями хранения и отказов.

История данных и ветвление уже доступны в готовых системах. Предполагаемое отличие Duro нужно искать в удобстве общего API и объёме работы, который остаётся у разработчика приложения.

## Базовый вариант на сервисе и БД

Приложение может хранить каждый вариант поездки под собственным ID и создавать копию выбранной версии. Транзакция БД позволяет записать изменения вместе с результатом запроса. Проверка ревизии или подходящий механизм сериализации защищает конкурентные правки.

Для небольшого приложения этого может быть достаточно. Поэтому пример плана поездки сам по себе не доказывает необходимость отдельной платформы.

Duro нужно сравнить с таким сервисом и с готовой объектной системой. Оба варианта должны одинаково обрабатывать потерянные ответы, повторные запросы и отказ исполнителя при доступном хранилище.

## Выбор модели сохранения

Рассматриваются два варианта событийной основы:

| Вариант | Обязанность приложения | Обязанность платформы |
| --- | --- | --- |
| Явный `storage` и журнал изменений | Читать и записывать значения, проверять предметные правила | Фиксировать изменения хранилища и воспроизводить их |
| Предметный Event Sourcing | Формировать события и определять их применение | Сохранять события и организовывать восстановление через прикладной обработчик |

В текущем предложении выбран первый вариант как отправная точка. Он ближе к способу работы с хранилищем Cloudflare. Обязательная пара `handle/apply` из прежнего предложения больше не задаёт публичную модель объекта.

По одной записи ключа нельзя определить смысл бизнес-операции. Если нужны автор, причина и предметное название события, приложение должно сохранять эти сведения. Пользу предметных событий можно проверить отдельно.

В MVP используется только KV API. SQL API находится за пределами MVP: для него потребуются захват фактических изменений и работа со схемами данных. Подробности приведены в [модели хранения](Concepts-Persistence.md).

## Требования к снимкам данных

Автоматическое сохранение памяти экземпляра добавило бы зависимость от runtime, состава памяти и ресурсов процесса. Такую возможность в текущую модель не включаем.

Логический снимок содержимого `storage` решает другую задачу: сокращает путь восстановления из журнала. Он не меняет способ написания методов и не сохраняет незаписанные поля.

Для небольшого объекта достаточно копирования данных при создании ветки и восстановления от начального состояния. Оптимизацию снимков и общей истории стоит выбирать по измерениям.

## Результаты анализа модели

| Вопрос | Вывод и граница |
| --- | --- |
| Можно ли объяснить модель на знакомом примере? | Да: один план содержит бюджет и расходы, а ветка представляет другой вариант |
| Разделены ли память и долговечные данные? | Да: в историю попадают явные записи через `storage` |
| Требуется ли автоматически сохранять класс или процесс? | Нет: воспроизводятся значения хранилища |
| Различаются ли чтение, ветка и откат? | Да: чтение не меняет текущие данные; ветка получает новый ID; откат создаёт новую ревизию исходного объекта |
| Что происходит с повторами после отката? | Сведения о завершённых запросах сохраняются вне откатываемых данных |
| Доказана ли польза отдельной платформы? | Пока нет: нужны реализации для сравнения и проверка интеграции |
| Проверены ли производительность и сбои? | Пока нет: описаны ожидаемые исходы |
| Подтверждён ли спрос? | Пока нет: пример служит для проверки модели |

Числа и последовательность операций разобраны в [плане поездки](Concepts-Trip.md). Они проверяют согласованность документации и не заменяют испытания распределённой реализации.

## Отложенные возможности

| Возможность | Причина | Условие возврата |
| --- | --- | --- |
| Полный SQL API | Нужно определить журналирование изменений и версий схемы | KV окажется недостаточно для выбранных приложений |
| Обязательные предметные события | Усложняют контракт прикладного кода | Появится подтверждённая потребность в семантической истории |
| CRDT и локальные реплики | Для первого примера достаточно серверных команд | Потребуются независимые правки без связи |
| Слияние веток | Нужны правила разрешения предметных противоречий | Приложение определит полезную операцию слияния |
| Ветвление нескольких объектов | Требуется общий срез и замена ссылок | Одного хранилища окажется недостаточно |
| Внешние действия и таймеры | Добавляют доставку, повторы и правила ветвления | Сценарий потребует автономной работы или интеграций |
| Общая история без копирования данных | Усложняет хранение и удаление | Измерения покажут высокую стоимость копирования |

Смена кода с миграциями не входит в MVP. В PoC версия фиксируется при создании объекта, а ветка наследует версию выбранной ревизии. Операция `migrate` должна сохранять новую версию вместе с преобразованными данными и оставлять старые ревизии доступными.

Откат является дополнительной операцией PoC. Он использует тот же журнал, но добавляет правила замены текущих данных и сохранения служебных результатов.

Лимиты размера объекта, записи и страницы истории, а также длины очереди заданы в [NFR-04](../requirements/nonfunctional/NFR-04.md). Квоты накопленной истории и результатов по объектам не входят в MVP.

## План проверки на прототипе

Для PoC нужен воспроизводимый сценарий плана поездки и подключение второго типа данных без изменения ядра Duro. Сравнение объёма интеграции с обычным сервисом и готовой объектной системой не входит в приёмку PoC.

Обязательные проверки охватывают явную запись, историческое чтение, создание ветки, потерянный ответ и запрет записи от прежнего владельца. Отдельно проверяется, что изменение поля экземпляра без `put` не попадает в сохранённые данные. Откат проверяется при его реализации.

Свежесть чтений, порядок команд, срок хранения результатов запросов, доступность старых ревизий и модель отказов заданы в [требованиях к PoC](../Requirements.md). Три модуля и протоколы выбранного поведения описаны в [архитектуре MVP](../Architecture-MVP.md); корректность реализации ещё предстоит проверить.
