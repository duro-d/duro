# Use Cases

Для PoC обязательны сценарии с UC-01 по UC-05 и UC-08. Их операции заданы в [функциональных требованиях](Functional-Requirements.md). UC-06 проверяет дополнительный откат при его реализации; UC-07 не входит в MVP. Достаточно демонстрационного скрипта или CLI, который выполняет действия клиентского приложения.

В примере тип `TripPlan` хранит бюджет и расходы. Метод `addExpense` принимает JSON с ID и суммой расхода. Приложение проверяет уникальность расхода и бюджет. Метод `getSummary` получает `null` и возвращает бюджет и общую сумму.

Сценарии используют указанные начальные состояния. Их можно проверять отдельно. Перед созданием, RPC-вызовом, ветвлением, откатом и обновлением кода клиент создаёт `request_id`. Для повторной отправки той же операции сохраняет этот ID и параметры.

## UC-01. Подключить тип и создать объект

**Основной участник:** разработчик. **Другие участники:** оператор и клиентское приложение.

**Цель:** подключить прикладной код и создать объект с начальными данными.

**Триггер:** разработчик подключает тип `TripPlan` к Duro.

**Предусловия:** стенд развёрнут, у разработчика есть токен API для загрузки кода; ID `trip/main` свободен.

**Основной поток:**

1. Разработчик описывает инициализацию и методы `addExpense`, `replaceExpensePrice`, `getSummary` версии `1` на документированном языке обработчиков.
2. Разработчик собирает пакет с манифестом и загружает его через API как тип `TripPlan` версии `1`, без пересборки или перезапуска исполнителей.
3. Duro проверяет пакет в поддерживаемой среде исполнения, сохраняет его вместе с регистрацией и возвращает список RPC-методов версии.
4. Клиент вызывает `create` с ID `trip/main`, типом `TripPlan`, версией `1`, `input: {budget: 1000}` и `request_id=create-main`.
5. Duro запускает инициализацию с пустым хранилищем. Она записывает бюджет и пустой список расходов.
6. Duro сохраняет объект, начальную ревизию `0` и результат запроса вместе.
7. Клиент получает ID и ревизию и открывает план пользователю.

**Другие исходы:**

- Пакет без нужных функций не регистрируется. Другое содержимое под занятой парой «тип, версия» не заменяет прежний код.
- Повтор создания с тем же `request_id` возвращает исходный результат. Занятый другим созданием ID не перезаписывается.
- Если инициализация не завершилась успешно, объекта нет.

**Результат:** тип зарегистрирован, существует план `trip/main@r0` с бюджетом 1000 без расходов. Ранее созданные объекты не изменились.

**Требования:** [FR-01](requirements/functional/FR-01.md), [FR-02](requirements/functional/FR-02.md).

## UC-02. Вызвать метод объекта

**Основной участник:** клиентское приложение.

**Цель:** добавить расход через RPC и при необходимости узнать доступные методы.

**Триггер:** пользователь добавляет дорогу за 200.

**Предусловия:** `trip/main@r0` использует код `1`, содержит бюджет 1000 и пустой список расходов.

**Основной поток:**

1. При необходимости клиент вызывает `describe("trip/main")` и получает тип, версию кода, ревизию и список методов. Известный метод можно вызвать без этого шага.
2. Клиент вызывает `invoke("trip/main", "addExpense", {id: "train", amount: 200}, {request_id: "add-train"})`.
3. Duro проверяет сохранённый результат до выбора исполнителя. Для нового запроса ставит вызов в очередь объекта и повторяет проверку перед запуском.
4. Для нового запроса метод читает бюджет и расходы, проверяет сумму и ID позиции.
5. Метод записывает новый список расходов и возвращает `{total: 200}`.
6. Duro сохраняет запись, историю `r1` и результат запроса вместе, затем возвращает ответ клиенту.
7. Клиент вызывает `getSummary` с аргументом `null` и новым `request_id` и получает сумму 200 без новой ревизии.

**Другие исходы:**

- Для отсутствующего ID объект не создаётся автоматически. Метод, которого нет в текущей версии, не запускается.
- При превышении бюджета метод возвращает предметный отказ без сохранения изменений. Отказ запоминается для повторов.
- Одновременный вызов ждёт своей очереди и работает с результатом предыдущего.
- Если ответ потерян, клиент повторяет вызов с `request_id=add-train` и прежними параметрами. Duro возвращает результат `r1` без повторного запуска метода.
- Если с тем же ID отправлен другой аргумент, вызов не выполняется.
- Если метод не возвращает значение, клиент получает `result: null` и ревизию после фиксации. Отсутствие значения не превращает вызов в фоновую задачу.

**Результат:** расход сохранён одной ревизией; завершённые повторы получают тот же результат. Новое действие требует нового `request_id`.

**Требования:** [FR-03](requirements/functional/FR-03.md), [FR-04](requirements/functional/FR-04.md).

## UC-03. Прочитать текущие данные

**Основной участник:** клиентское приложение.

**Цель:** показать текущий план.

**Триггер:** пользователь открывает или обновляет план.

**Предусловия:** объект существует.

**Основной поток:**

1. Клиент вызывает `read("trip/main")`.
2. Duro читает одну сохранённую ревизию.
3. Возвращает бюджет, расходы, номер ревизии и версию кода.
4. Клиент показывает план пользователю.

**Другие исходы:** при одновременной записи возвращается состояние до неё или после неё целиком. При недоступной БД старый кеш не выдаётся за текущее состояние.

**Результат:** клиент получил данные одной ревизии; объект не изменился.

**Требование:** [FR-05](requirements/functional/FR-05.md).

## UC-04. Просмотреть историю и прошлую ревизию

**Основной участник:** клиентское приложение.

**Цель:** показать историю изменений и данные выбранной ревизии, сохранив текущий план.

**Триггер:** пользователь открывает историю и выбирает `r2`.

**Предусловия:** план имеет ревизии `r0`–`r3`. В `r2` есть дорога 200 и жильё 500; в `r3` дополнительно есть занятие 100.

**Основной поток:**

1. Клиент вызывает `history("trip/main", {limit: 2})`.
2. Duro фиксирует верхнюю границу обхода `r3` и возвращает `r0`, `r1` с курсором.
3. Клиент передаёт курсор и получает `r2`, `r3`. Курсор следующей страницы равен `null`.
4. Клиент вызывает `readRevision("trip/main", 2)`.
5. Duro восстанавливает данные `r2` без запуска прикладных методов и возвращает их с версией кода этой ревизии.
6. Клиент показывает прежний план с суммой 700.

**Другие исходы:**

- Если во время просмотра появилась `r4`, она не включается в начатый обход. Для неё клиент начинает новый обход.
- Несуществующая ревизия не возвращает данные другой ревизии.

**Результат:** история показана без пропусков и повторов. Пользователь видит данные `r2`, а текущий объект остаётся на `r3` или более поздней конкурентной ревизии.

**Требования:** [FR-06](requirements/functional/FR-06.md), [FR-07](requirements/functional/FR-07.md).

## UC-05. Создать независимый вариант

**Основной участник:** клиентское приложение.

**Цель:** изменить копию плана, сохранив оригинал.

**Триггер:** пользователь выбирает создание варианта из `r2`.

**Предусловия:** `trip/main@r2` доступен, его пакет кода сохранён в Duro и доступен для загрузки; ID `trip/alternate` свободен.

**Основной поток:**

1. Клиент вызывает `fork` с источником `trip/main`, ревизией `2` и целевым ID `trip/alternate`, передавая `request_id=fork-alternate`.
2. Duro создаёт новый объект с данными на 700, версией кода исходной ревизии и собственной ревизией `0`.
3. Duro сохраняет происхождение ветки и возвращает её ID.
4. Клиент вызывает методы нового объекта. Исходный план не меняется.

**Другие исходы:** повтор завершённого запроса возвращает ту же ветку. При ID, занятом другим созданием, ветка не создаётся и существующий объект не меняется. Изменения источника после `r2` не попадают в ветку.

**Результат:** существуют два независимых объекта. Даже если текущая версия кода источника уже другая, ветка использует код выбранной ревизии.

**Требование:** [FR-08](requirements/functional/FR-08.md).

## UC-06. Вернуть прежние данные

Дополнительный сценарий, проверяется при реализации FR-09. В демонстрации откат выполняется без параллельного редактирования.

**Основной участник:** клиентское приложение.

**Цель:** заменить текущие данные прежними, сохранив историю.

**Триггер:** пользователь выбирает откат к `r2`.

**Предусловия:** текущая ревизия – `r3`; `r2` и `r3` используют версию кода `1`.

**Основной поток:**

1. Клиент вызывает `restore("trip/main", {source_revision: 2, request_id: "restore-main"})`.
2. Duro ждёт очереди операции и заменяет все пользовательские данные содержимым `r2`.
3. Сохраняет замену как `r4` и пересоздаёт экземпляр.
4. Клиент получает ревизию `4` и читает сумму 700.

**Другие исходы:**

- Если перед откатом другой метод успел сохранить изменение, откат заменяет и его данные. Отдельной проверки прочитанной клиентом ревизии нет.
- Если версии кода текущего объекта и выбранной ревизии различаются, откат не выполняется. Пользователь может создать ветку из старой ревизии.

**Результат:** текущая сумма – 700, `r3` с суммой 800 остаётся в истории, ветки не меняются. Повтор с тем же `request_id` возвращает результат `r4` без новой ревизии. Запоздалый повтор старого метода также возвращает прежний ответ и не применяет отменённое изменение.

**Требование:** [FR-09](requirements/functional/FR-09.md).

## UC-07. Обновить код объекта

Сценарий не входит в реализацию и приёмку PoC.

**Основной участник:** оператор. **Другой участник:** разработчик.

**Цель:** перевести существующий объект на новую версию без потери данных.

**Триггер:** разработчик подготовил `TripPlan` версии `2`.

**Предусловия:** `trip/main@r4` использует версию `1`. Пакет версии `2` загружен в Duro и зарегистрирован; её `migrate` добавляет поле `currency: "RUB"` к прежним данным.

**Основной поток:**

1. Оператор вызывает `updateCode("trip/main", {code_version: "2", request_id: "update-main-v2"})`.
2. Duro ждёт завершения предыдущего метода объекта.
3. Запускает `migrate` версии `2` с номером прежней версии `1`.
4. Функция добавляет валюту через `storage.put`.
5. Duro сохраняет данные, версию `2`, запись истории `r5` и результат запроса одной транзакцией.
6. Пересоздаёт экземпляр. Новые вызовы используют методы версии `2`.
7. Оператор читает сведения об объекте и проверяет версию и список методов.

**Другие исходы:**

- Преобразование не завершилось: код, данные и ревизия остаются прежними.
- Повтор с `request_id=update-main-v2` возвращает исходный результат без преобразования.
- Для нового запроса версия уже равна `2`: Duro сохраняет результат с текущей ревизией без запуска преобразования.
- Между постановкой RPC-вызова в очередь и его запуском сменился код: вызов проверяется и выполняется по новой версии. Если прежнего метода в ней нет, он не запускается.

**Результат:** ID объекта сохранён, `r5` использует версию `2`. Старые ревизии и независимые ветки сохраняют свои версии.

**Требование:** [FR-10](requirements/functional/FR-10.md).

## UC-08. Восстановить обслуживание после отказа

**Основной участник:** оператор, проверяющий восстановление. **Другой участник:** клиентское приложение.

**Цель:** возобновить работу объекта на другом исполнителе и проверить готовность компонентов.

**Триггер:** исполнитель аварийно остановлен.

**Предусловия:** работают два исполнителя и БД; остальные компоненты доступны.

**Основной поток:**

1. Оператор останавливает процесс-исполнитель во время вызова метода.
2. Duro обнаруживает остановку и передаёт право записи другому исполнителю.
3. Новый исполнитель загружает последние сохранённые данные и пакет нужной версии кода, в том числе при пустом кеше, без повторной инициализации.
4. Оператор запрашивает состояние и готовность работающего исполнителя. Тот проверяет доступность хранения, загрузки пакетов и своей среды исполнения.
5. Клиент отправляет изменяющий RPC-вызов по прежнему ID с новым `request_id`. До успешного ответа повторяет его раз в секунду с тем же ID запроса и параметрами.
6. Оператор проверяет данные и историю. Время восстановления считается от остановки до успешного ответа; по журналам подтверждается выполнение команды другим исполнителем.

**Другие исходы:**

- Остановка до сохранения: записи прерванного метода отсутствуют. Клиент может повторить исходный вызов с прежним `request_id`.
- Остановка после сохранения до ответа: клиент повторяет вызов с прежним `request_id` и получает сохранённый ответ без повторного запуска метода.
- Старый исполнитель возобновил работу: его прежние права не позволяют записать данные.
- При потере связи с БД процесс может отвечать, но готовность отрицательная. После возврата связи проверка готовности проходит; время восстановления при недоступной БД в лимит 30 секунд не входит.

**Результат:** при доступной БД изменяющий RPC-вызов успешно выполняется другим исполнителем не позднее 30 секунд после остановки первого. Одного успешного чтения недостаточно для подтверждения восстановления. Клиент не меняет адрес API и ID объекта. Проверки состояния не раскрывают данные объектов и секреты.

**Требования:** [FR-11](requirements/functional/FR-11.md), [FR-12](requirements/functional/FR-12.md).
