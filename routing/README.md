# Маршрутизатор Duro

Go-сервис принимает HTTP-запросы, находит владельца объекта и передаёт вызов исполнителю по gRPC. Можно запустить несколько экземпляров. Для создания объектов, переноса и восстановления они выбирают одного контроллера через etcd. Сервис состояния хранит назначение и проверяет поколение при записи. [RFC 001](https://github.com/duro-d/duro/pull/9) · [Схемы внутренних RPC](../api/README.md)

## Проверка с заглушками

Нужны Go 1.25 или новее, Python 3.9 или новее и запущенный Docker. Выполни из каталога `routing`:

```sh
go test -race ./...
python3 e2e/run.py --policy hrw --artifacts /tmp/duro-hrw
python3 e2e/run.py --policy load --artifacts /tmp/duro-load
```

Каждый прогон собирает отдельные бинарники, запускает собственный контейнер etcd 3.6.5, два маршрутизатора и один процесс заглушек. Сервис состояния и два исполнителя слушают разные gRPC-порты на loopback. Скрипт дожидается выбора контроллера и отправляет запросы через обе реплики. После завершения он останавливает процессы и удаляет свой контейнер.

Сценарии регистрируют аукцион и квоту, создают объект через ведомый маршрутизатор и проверяют чтение с обеих реплик. Повтор после потери ответа должен вернуть прежний результат. Два одновременных списания с одним ID должны изменить остаток один раз. После ручного переноса, остановки лидера и отказа владельца проверяются новое поколение, запрет записи старому владельцу и итоговый остаток. Шаги и время восстановления сохраняются в `scenarios.json`, рядом лежат JSON-журналы и снимок метрик.

В тестовом процессе хранятся данные в памяти, а два примера обработчиков исполняются на Go. Через сеть проходят настоящие сообщения Protobuf. Такой прогон проверяет маршрут, содержимое сообщений и поведение при отказах. Долговечность при потере primary и время восстановления после отказа VM проверяются отдельно с настоящим хранением. Сравнение производительности по NFR-05 требует реального runtime, согласованного оборудования и численных целей.

## Запуск вручную

В отдельном локальном etcd выдели префикс `/duro/` для этого стенда. Адрес по умолчанию — `127.0.0.1:2379`. У процессов исполнителей разные ID. Под `/duro/workers/{worker_id}` каждый размещает свой gRPC-адрес на аренде etcd. На каждом перезапуске настоящего исполнителя выдай новый ID процесса. Команда ниже запускает тестовые процессы с заранее известными ID:

```sh
go run ./cmd/mock -etcd 127.0.0.1:2379 -state-listen 127.0.0.1:7100 \
  -workers a=127.0.0.1:7101,b=127.0.0.1:7102 -admin-listen 127.0.0.1:7109
```

Установи `DURO_TOKEN` для публичного API и отдельный `DURO_CONTROLLER_TOKEN` для связи между маршрутизаторами. Обе реплики используют одни и те же значения. В двух терминалах из каталога `routing` запусти:

```sh
go run ./cmd/router -listen 127.0.0.1:8080 -private-listen 127.0.0.1:18081 -policy hrw
go run ./cmd/router -listen 127.0.0.1:8082 -private-listen 127.0.0.1:18082 -policy hrw
```

Оба маршрутизатора принимают пять операций `POST /v1/{operation}` с заголовком `Authorization: Bearer …`. Способ регистрации JS-пакета и примеры для всех пяти операций есть в [сквозном сценарии](e2e/run.py). Пакет [sdk](sdk/client.go) принимает список адресов. `PrepareCreate` и `PrepareInvoke` возвращают ID запроса до отправки. После неопределённого исхода можно повторно вызвать `Do` с тем же подготовленным запросом. Код, HTTP-статус и признак неопределённого исхода возвращаются в `sdk.Error`.

На публичном адресе доступны `/healthz` и `/readyz`. На приватном адресе лежит `/metrics`. На избранном контроллере оператор может передать объект через `POST /admin/move` с токеном контроллера и телом `{"object_id":"q","target":"b"}`. Дай приватный адрес только участникам стенда. Для отдельных сетевых пространств укажи достижимый адрес этого процесса флагом `-advertise`. В PoC внутренние соединения используют сеть доверенного стенда.

## Устройство модуля

| Пакет | Ответственность |
| --- | --- |
| internal/gateway | Авторизация, лимиты HTTP, бюджет времени, кеш назначений, условное обновление при устаревшем поколении |
| internal/cluster | Регистрации в etcd, выборы, обращение ведомой реплики к контроллеру |
| internal/controller | Резервация создания, продление аренды, перенос, восстановление незаконченных назначений |
| internal/placement | Детерминированный HRW, размещение по нагрузке, отбор кандидатов для ограниченного переноса |
| internal/teststand и cmd/mock | Контрактные заглушки и точки отказа для независимой проверки |
